# Horizon v1.1.2 Design Specification

## Objective

Version 1.1.2 adds three operator-facing capabilities: a **local adaptive energy forecast**, a **high-contrast advanced dark theme**, and **dashboard widgets that users can show, hide, and reorder**. It also defines a stable integration surface so external modules can provide energy samples and consume normalized state without direct access to stored credentials.

## Energy Forecast Contract

The release implements an explainable **time-of-day weighted forecast**, not a claim of a cloud-trained or universally accurate AI model. It accepts timestamped household energy samples, calculates hourly historical baselines and a recent weighted baseline, then produces a 24-hour prediction with confidence bounds. Forecast quality is proportional to the quantity and variability of actual submitted data.

| Input | Rule | Purpose |
| --- | --- | --- |
| `timestamp` | ISO-8601 UTC string | Retains an auditable source time for each measurement. |
| `hour` | Integer from 0–23 | Selects comparable time-of-day history without requiring a device clock in the core. |
| `usageKw` | Finite non-negative number | Measured whole-home or normalized circuit consumption. |
| `horizonHours` | Integer from 1–48; default 24 | Bounds forecast cost and user-visible range. |

The forecast uses a 75% hourly historical baseline and a 25% exponentially weighted recent baseline. Its confidence is derived from observation count and the coefficient of variation; the response reports the confidence and an uncertainty band instead of hiding data quality. Fewer than six samples returns a validation error. Production accuracy claims require a back-test against at least 30 days of real data and should report MAE and MAPE.

## Dashboard Customization

Widget preferences are a non-sensitive device preference stored by the UI, never bundled into a Home Assistant credential. The default dashboard has five widgets: home status, energy flow, live activity, favorite devices, and the new next-24-hours forecast. Operators can hide a widget, restore defaults, and move a widget up or down. The default order is restored whenever no valid stored preference exists.

The theme selector supports **System**, **Light**, and **Dark**. System follows the operating-system color preference. The dark palette uses a high-contrast surface hierarchy, focus treatment, and status colors rather than merely inverting the light palette.

## Extension API Direction

The primary v1.1.2 extension surface consists of typed Tauri commands, and a versioned plugin manifest format for future adapters. Tauri commands offer typed async request/response operations; dynamic streaming state should use a Tauri channel or event only when ordered delivery is not required. [1] The core plugin model supports a Rust crate plus optional JavaScript API bindings, with explicit command permissions for every exposed operation. [2]

| API family | v1.1.2 availability | Purpose |
| --- | --- | --- |
| Energy forecast | Implemented | Submit samples and retrieve a local forecast. |
| Home Assistant connection | Implemented | Connect, discover supported entities, control compatible actuators, and disconnect. |
| Module manifest | Documented contract | Describes module identity, capabilities, and schema version for a future signed-plugin runtime. |
| Live event stream | Documented roadmap | Home Assistant’s authenticated WebSocket supports state subscriptions; integration is deferred until reconnect and ordering tests exist. [3] |

## Security and Compatibility Decisions

Third-party modules must not receive the Home Assistant access token. They provide normalized data to Horizon or receive a scoped command response. A future plugin runtime must use explicit capabilities and permissions, validate schemas at the boundary, maintain per-module audit records, and prevent untrusted modules from making arbitrary network or file-system calls.

The current Home Assistant REST integration continues to use bearer-token calls for `/api/states` and compatible `/api/services/{domain}/{service}` operations. [4]
